# S128: frontend v2.0.0 → v3.0.1 patch re-derivation

`lib/frontend.sh` clones the upstream frontend at a pinned tag and applies
two mechanical patches (`frontend::_patch_uistore`,
`frontend::_patch_entrypoint`) so the shipped image gates its feature tabs
off `ENABLED_FEATURES` instead of Keycloak roles. S128 bumps the pinned
tag `v2.0.0` → `v3.0.1` (`FRONTEND_IMAGE_TAG` becomes
`f13-frontend:v3.0.1_based`) and re-derives both patches against the real
v3.0.1 source, per the PRD's "do not force a mismatched patch" rule.

Both repos were cloned read-only for comparison (`--depth 1 --branch
<tag>` from `gitlab.opencode.de/f13/microservices/frontend.git`), never
hand-derived from memory.

## `docker-entrypoint.sh` patch — unchanged, verified only

`scripts/docker-entrypoint.sh` grew several new config fields between
v2.0.0 and v3.0.1 (`KEYCLOAK_LOGOUT_PATH`, `ADD_TRANSCRIPTION_JOB_ID_TO_ARTIFACTS`,
`CHAT_CHAR_LIMIT`, `CHAT_CONTEXT_SAFE_TOKENS`), but the two anchors the
patch depends on are structurally identical:

- The first `=$(escape_js_string ...)` assignment line inside
  `generate_config_script` is still `api_url=$(escape_js_string
  "${API_URL:-}")` — not inside the `escape_js_string() { ... }`
  definition itself, so the injected `enabled_features=$(escape_js_string
  ...)` line still lands in the right place (no infinite-recursion
  regression).
- The single-line heredoc `<script>window.APP_CONFIG={...};</script>`
  still ends in `"};</script>"`, so the `sub(/\};<\/script>/, ...)` still
  fires and appends `ENABLED_FEATURES` to the object.

Verified by running `frontend::_patch_entrypoint` against the real
v3.0.1 `scripts/docker-entrypoint.sh`: `bash -n` passes, exactly two
`ENABLED_FEATURES` occurrences (the assignment and the object field),
and the file stays 0755. No code change needed for this half of S16.

## `UIStore.js` patch — re-derived (mismatch found and fixed)

v3.0.1 adds a nested `tools: { onlineSearch, skills }` sub-object to the
`featureStore` shape that did not exist in v2.0.0:

```js
: // If Keycloak is disabled, most features are enabled by default
    writable({
      chat: true,
      recherche: true,
      askTheText: false,
      summary: true,
      transcription: true,
      feedback: true,
      tools: {
        onlineSearch: true,
        skills: false,
      },
    });
```

`userInfo.subscribe()` unconditionally reads `features.tools.onlineSearch`
and `features.tools.skills` on every update — including when Keycloak is
disabled. The pre-S128 patch's replacement object (ported verbatim from
the v2.0.0 shape) dropped the `tools` key entirely, which would have
thrown `TypeError: Cannot read properties of undefined (reading
'onlineSearch')` the first time `userInfo` emits with Keycloak disabled.
This was caught by diffing the patched output against the real v3.0.1
file before shipping, not by a v130 runtime smoke (the sandbox has no
Docker).

**Fix:** the replacement object generated by
`frontend::_patch_uistore`'s awk script now includes the same nested
shape, computed off two additional entries in the `enabled` list:

```js
tools: {
  onlineSearch: enabled.includes('onlineSearch'),
  skills:       enabled.includes('skills'),
},
```

The no-`ENABLED_FEATURES`-set fallback default also gained
`onlineSearch` (`'chat,recherche,askTheText,summary,transcription,feedback,onlineSearch'`)
to preserve the v2.0.0-era default behavior (online search on, skills
off) when the env var is unset — matching the original hardcoded
`tools: { onlineSearch: true, skills: false }`.

`ENABLED_FEATURES` itself is still set to `"chat"` only by the wizard
(`bin/f13-config`, minimal preset), so in practice both `tools` flags
render `false` on a wizard-generated stack — RAG/websearch/skills are
out of scope for this configurator regardless.

## What was NOT re-derived

- `agentic_chat.yml` / chat-side config — out of scope for this story;
  covered by S125/S126 against `docs/upstream/v3/chat/`.
- The GUI's cosmetic service-image list
  (`gui/src/routes/status/+page.svelte`, `services` array) still shows
  `f13-frontend:v2.0.0_based`, `core:v2.0.0`, `chat:v1.2.0`, and
  `postgres:17-alpine` — display-only strings, already stale from
  S122–S124 (which correctly left them for the GUI track). Left alone
  here for the same reason: it's a `gui/` file requiring the GUI
  backpressure track (`npm run check && npm run test:unit && cargo
  check`), and Phase 17's loop-runnable stories are shell-track only.
  S129 (regression sweep) or a follow-up GUI story should sync it.
- README.md's preset table (`core:v2.0.0`, `chat:v1.2.0`,
  `postgres:17-alpine`) — deliberately left for S129's dedicated
  "README/docs describe the new topology" sweep, per the same call
  S122 made.
